k8s-cost-radar

Making a cluster’s declared resource costs easier to investigate.

Format
Command-line tool
Built with
Python, Click, Rich
Try it
Demo without a cluster

A cluster can have a lot of resource requests without a clear explanation of what they add up to. I built k8s-cost-radar to make that footprint visible at the Pod, namespace, and cluster level.

Explore the source on GitHub ↗

The problem

Before changing a workload, an engineer needs a useful starting point: which namespaces account for the declared capacity, which Pods have missing requests, and which settings deserve a closer look. That investigation should be possible without first operating another dashboard service.

One report, three levels of detail

  1. 01
    Read requestsLoad Pod resource configuration from Kubernetes, or use mock data in demo mode.
  2. 02
    Estimate and flagApply configurable CPU and memory rates; identify settings to investigate.
  3. 03
    SummarizeGroup the results by Pod, namespace, and cluster.
  4. 04
    ExportRead a terminal table or take the report into JSON or Markdown.

The useful constraint: a small, explicit model

The estimate multiplies CPU and memory requests by configurable hourly rates and a fixed 730-hour month. Keeping that calculation visible makes the assumptions easy to challenge.

monthly estimate = 730 × (
  CPU requested × CPU hourly rate
  + memory requested × memory hourly rate
)

This attributes cost to declared capacity. It does not reconcile an invoice, account for instance packing, or measure actual utilization. The code also labels binary memory quantities as GB; rates need compatible units for a meaningful comparison.

Why a command-line tool

The CLI keeps the workflow close to the engineer’s existing tools. Rich renders the human-readable report; dataclasses carry the Pod and summary records; Click exposes the scan and export options. JSON and Markdown outputs make the findings easier to inspect or include in a review.

Demo mode creates mock workloads so the reporting flow can be explored without cluster access. Its data varies between runs, so a demo total is not a benchmark or evidence of achieved savings.

Run the demo

From a local checkout of the public repository:

python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python k8s_cost_radar.py demo
python k8s_cost_radar.py demo --output md

The demo does not need kubeconfig. A real scan uses the local Kubernetes context, so check that context and its read permissions before running it.

What the recommendations cannot prove

The current heuristics flag large requests, missing requests, and large limit-to-request ratios. Those are investigation prompts. A high ratio does not establish that a request is excessive, and lowering a request without usage evidence can make scheduling less representative of actual demand.

The reported “potential savings” is a rough heuristic. It is not a measured saving or a reason to resize automatically. Storage, network charges, commitment discounts, and real utilization sit outside the current model.

What I would improve next

The next useful step is to connect historical utilization to the report, make unit handling more explicit, and separate configuration warnings from cost recommendations. That would let the tool explain why a proposed change is supported by measurements.
