Kubernetes Production Readiness: What Actually Matters

February 7, 2026 8 min read

I've migrated half a dozen companies to Kubernetes. Every time, the same patterns emerge: teams obsess over the wrong things early on, then scramble to fix the basics when things break at 2am. Here's what actually matters when running K8s in production.

The Reality Check

Your first Kubernetes cluster will work fine. Your second cluster will have mysterious networking issues. Your third cluster will teach you that resource limits actually matter. By the fourth, you'll have a runbook for "why can't pods talk to each other" that's longer than your resume.

This isn't a comprehensive guide. This is what breaks first.

1. Resource Limits (Actually Set Them)

Everyone knows you're supposed to set resource requests and limits. Almost nobody does it properly until a single pod eats all available memory and takes down the node.

What works:

  • Start with requests based on actual usage (check your metrics)
  • Set limits 20–30% above requests as a buffer
  • Use LimitRange to enforce defaults — don't trust developers to remember
  • Enable vertical pod autoscaling for workloads with unpredictable resource needs

What breaks:

  • No limits → one bad deploy kills the cluster
  • Limits way higher than requests → scheduler gets confused, nodes overcommit
  • Requests too low → constant evictions and restarts

2. Networking (The DNS Always Breaks First)

Kubernetes networking looks simple in the diagrams. In production, it's where most incidents start.

CoreDNS is your canary:

  • Scale CoreDNS pods based on cluster size (2 pods won't cut it for 100+ services)
  • Monitor DNS query latency — if it spikes, you're about to have a bad time
  • Enable DNS caching at the node level with NodeLocal DNSCache
  • Set proper connection limits and timeouts

Network Policies (actually use them):

Don't wait until compliance asks. Start with a default-deny policy and explicitly allow what's needed. Yes, it's annoying. Yes, it'll save you when someone deploys a cryptominer.

3. Observability Before You Need It

You can't troubleshoot what you can't see. Set this up before your first production deploy.

Minimum viable observability stack:

  • Metrics: Prometheus + Grafana (or managed equivalent)
  • Logs: Centralized logging (Loki, CloudWatch, whatever — just pick one)
  • Traces: Can wait initially, but you'll want it when debugging microservices
  • Dashboards: Node utilization, pod status, ingress traffic, DNS latency

Alert on what matters:

  • Node NotReady for > 2 minutes
  • Pod CrashLoopBackOff
  • PersistentVolume claim pending > 5 minutes
  • DNS query failures > 1%
  • API server latency p95 > 1s

4. Autoscaling (Start Simple)

Horizontal Pod Autoscaling works. Cluster autoscaling is trickier. Vertical pod autoscaling is still rough around the edges.

HPA basics:

  • Start with CPU-based autoscaling (it's good enough for most workloads)
  • Set min replicas to handle baseline traffic
  • Test your HPA under load — scaling up is easy, scaling down gracefully is hard
  • Use PodDisruptionBudget to prevent autoscaling from breaking during deployments

Cluster autoscaling gotchas:

  • New nodes take 2–5 minutes to become ready — your app needs to handle that lag
  • Mix of on-demand and spot instances needs careful config
  • Scale-down can be overly aggressive — tune scale-down-delay-after-add

5. Security (Do This First)

Kubernetes security is a marathon, but some things need to happen immediately.

Day 1 security:

  • RBAC: Don't give admin to everyone. Use namespaces and role bindings properly.
  • Pod Security Standards: Enforce restricted profile for production namespaces
  • Network Policies: Default deny, explicit allows
  • Secret Management: External secrets operator + Vault / AWS Secrets Manager
  • Image Scanning: Scan on push, block high/critical CVEs in production

Don't run as root:

securityContext:
  runAsNonRoot: true
  runAsUser: 1000
  allowPrivilegeEscalation: false
  capabilities:
    drop:
      - ALL

6. Persistent Storage (It Will Bite You)

StatefulSets look simple in demos. In production, storage is where you'll spend most of your time troubleshooting.

Storage class decisions:

  • Use managed storage (EBS, Azure Disks, GCE PD) unless you have a very good reason not to
  • Set proper IOPS and throughput limits
  • Enable volume snapshots and test restores
  • Monitor PV usage — running out of space in a pod is a terrible way to debug

Backup strategy:

Velero or equivalent. Schedule regular backups. Actually test restores. The day you need them, you'll be glad you did.

7. Deployment Strategy (Rollouts That Don't Break Things)

Rolling updates are the default. They're also the most common source of self-inflicted outages.

Safe rollout config:

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 0
    maxSurge: 1
readinessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
livenessProbe:
  httpGet:
    path: /health
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10

Why this matters:

  • maxUnavailable: 0 ensures you always have capacity
  • Proper readiness probes prevent routing traffic to pods that aren't ready
  • Liveness probes restart unhealthy pods (but tune them — too aggressive kills healthy pods under load)

What You Can Skip (For Now)

Kubernetes has a lot of features. You don't need all of them on day one.

Save for later:

  • Service mesh (Istio / Linkerd) — unless you have 50+ microservices, you don't need it yet
  • Multi-cluster setups — get one cluster stable first
  • Custom schedulers — the default works fine for most workloads
  • Advanced workload types (DaemonSets, Jobs, CronJobs) — learn them as needed

The Real Production Readiness Checklist

Here's what I check before calling a K8s cluster production-ready:

  1. All pods have resource requests and limits set
  2. Network policies in place (default deny)
  3. RBAC configured (no cluster-admin in production)
  4. Monitoring and alerting configured and tested
  5. Log aggregation working
  6. Backup/restore tested for stateful workloads
  7. Readiness and liveness probes on all deployments
  8. PodDisruptionBudgets for critical services
  9. Cluster autoscaling tested under load
  10. Incident runbooks written for common failures

Final Thoughts

Kubernetes is powerful, but it's not magic. It gives you the tools to run reliable systems, but you still have to use them properly. Start with the basics. Get monitoring right. Test your failure scenarios. Build your understanding incrementally.

The best Kubernetes setup is the one that doesn't wake you up at 3am because DNS is down again.
