Kubernetes Production Readiness: What Actually Matters

February 7, 2026 3 min read

Updated September 4, 2026

A deployment becoming Ready is a starting point. Production readiness means understanding what happens when traffic changes, a dependency fails, a node disappears, or the next release needs to be reversed.

Give resource settings a reason

The scheduler uses resource requests to place Pods. Limits have a different purpose: CPU limits constrain execution through throttling; memory limits can lead to an out-of-memory kill. A large gap between requests and limits does not confuse the scheduler, but low requests can leave less headroom than a workload actually needs. See Kubernetes resource management.

Choose values using representative measurements, including startup and peak demand. Review CPU and memory separately. A universal “20–30% above requests” rule cannot account for different workloads. Treat autoscaler recommendations as inputs to review, and test changes against latency and failure rates.

Use probes for distinct questions

Readiness asks whether a container should receive traffic. Liveness asks whether it needs restarting. A startup probe can allow a slow initialization before the other probes begin. Making liveness depend on a temporarily unavailable database can turn a dependency problem into repeated restarts. The probe documentation explains their separate behavior.

Test the endpoints and thresholds under load. Document what each probe checks, and how long a new instance normally needs before it can serve requests.

Test drains and deployments separately

A PodDisruptionBudget constrains supported voluntary evictions, such as a node drain. It cannot prevent an involuntary node failure, and it does not control a Deployment’s rolling-update strategy. Configure the rollout separately and test both paths. See disruption budgets and their limits.

For a rollout, check replica count, surge capacity, readiness, and graceful shutdown together. A setting such as maxUnavailable: 0 does not create spare capacity or guarantee that the application can serve traffic. Verify what happens when new Pods cannot be scheduled.

Make failure visible

Start with the signals needed to understand the service: request errors, latency, traffic, resource pressure, and dependency health. Add cluster and DNS signals that explain those symptoms. Each actionable alert needs an owner and a runbook; choose thresholds from service objectives and observed behavior.

My observability reference stack groups dashboard definitions and alert rules for this work. It still needs datasource wiring, metric-label alignment, and validation with the application being monitored.

Exercise the recovery procedure

Restore a stateful workload from backup into an isolated environment and check its data. Record the time taken and what remained unavailable. Test a failed deployment, a lost node, and a downstream timeout. A written procedure becomes more useful after someone other than its author has followed it.

Review access at the same time: service-account permissions, secret handling, and required network paths. Keep exceptions specific and documented. A default-deny policy needs explicit allowances for the traffic the service depends on, including DNS.

Evidence to bring to the review

  • Load-test results supporting resource settings and replica counts.
  • Probe behavior during startup, overload, and dependency failure.
  • Results from a node drain and a failed rollout.
  • An alert that reaches the right person with a usable runbook.
  • A tested restore with measured recovery time.

Those artifacts tell a more useful story than a list of installed Kubernetes add-ons.
