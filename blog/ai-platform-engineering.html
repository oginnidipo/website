AI Platform Engineering: What Teams Need Before They Ship Agents

May 10, 2026 3 min read

Updated September 4, 2026

An agent that can answer a question still needs an operating model. Before giving it access to a production system, I want to know how a wrong answer becomes visible, who owns the response, and how to stop an action already in progress.

Start with one bounded job

“Help the on-call engineer” is too broad to evaluate. “Summarize this incident using these logs and link each finding to its source” is a more useful starting point. Define the inputs, the allowed tools, the expected output, and the conditions that require a person.

Give the service an owner and a runbook. Product behavior, infrastructure reliability, and data access may belong to different teams, but the route from a failed request to the responsible person should be explicit.

Evaluate the whole task

Build a small evaluation set from representative tasks, including missing evidence, ambiguous requests, and tool failures. Check whether the answer is supported, whether the tool arguments are correct, and whether the system respects its access boundaries. Track latency and cost alongside task quality.

Keep the evaluation inputs and results tied to the release: prompt version, model configuration, retrieval setup, and tool definitions. A change in any of those can alter behavior. Review failed examples as well as aggregate scores; an average can hide an unacceptable failure.

Observe without collecting everything

A successful HTTP response does not establish that an answer was useful. Record the task outcome, tool-call status, timings, token usage, and relevant version identifiers. Where a trace needs content, redact sensitive fields and decide who can access it and when it expires.

Avoid logging full prompts and retrieved documents by default. They may contain customer data or secrets. OpenTelemetry’s GenAI conventions are a useful reference when choosing how to represent these operations.

Make permissions enforceable

Use a read-only tool for inspection tasks. For changes, distinguish between actions requiring approval and narrowly bounded actions the system may take itself. Those are design choices for the task, not fixed percentages of all use cases.

Enforce authorization in the tool or service handling the request. A sentence in a prompt cannot substitute for that boundary. For an approved action, bind the approval to the exact target and proposed change. Use idempotency where a retried call could otherwise perform the same mutation twice.

Plan the stop and recovery paths

Set a maximum number of tool calls, a time budget, and a cost budget. Repeated failures should produce a useful escalation with the last known state. Reaching a limit should not trigger another unbounded loop.

Retain a known-good configuration and test how to restore it. Reverting a prompt does not undo an email, a payment, or an infrastructure change. Those actions need their own recovery procedure. Model availability and retrieval data can also constrain what a rollback can restore.

Keep a release checklist

  • A named owner and an escalation path.
  • Representative evaluations, including failures and access violations.
  • Tool permissions and action approvals enforced outside the model.
  • Useful traces with intentional data handling.
  • Tested stop conditions and recovery procedures.

These are the questions I would bring to a design review. The answers should be concrete enough that another engineer can test them.
