AI Platform Engineering: What Teams Need Before They Ship Agents

May 10, 2026 9 min read

Every team I've watched ship an AI feature to production has hit the same wall: the model works in a notebook, but the system around it doesn't. Agents hallucinate, costs spike, latency degrades, and nobody knows who owns the incident. The failures are not model problems. They are platform problems. Here's the operating model I use to avoid them.

1. Define Ownership Before You Define Architecture

In most companies, AI features sit in a no-man's land between the ML team, the platform team, and product engineering. When an AI endpoint starts returning garbage at 2am, the pager goes to the on-call SRE who has never seen a prompt template. The SRE restarts the pod, the problem goes away for 20 minutes, then it comes back worse.

The fix is boring but non-negotiable: decide who owns the AI system's reliability, cost, security, and feature behavior before you build it. In practice, I split it like this:

  • Platform team: infrastructure, scaling, cost guardrails, observability, access control, model routing
  • Product engineering: prompt logic, retrieval pipelines, user-facing behavior, evaluation criteria
  • ML/AI team (if one exists): model selection, fine-tuning, benchmark evaluation, data pipelines

Everyone gets a runbook. Everyone gets a dashboard. Everyone knows what they are allowed to change without approval and what requires a second set of eyes.

2. Evaluations Are Your Test Suite

You would not deploy a microservice without unit tests. You should not deploy an AI feature without evals. An evaluation harness is not a research luxury; it is production infrastructure. I treat it exactly like CI: every prompt change, model swap, or retrieval pipeline update runs through the eval suite before it reaches staging.

What I measure depends on the use case, but the baseline set is consistent:

  • Accuracy / correctness: Does the output match the expected answer on a held-out test set?
  • Hallucination rate: Does the model invent facts, URLs, or configuration values?
  • Latency distribution: P50, P95, P99 for token generation and end-to-end response time
  • Cost per request: Token count × model price, tracked per user, per feature, per team
  • Safety / policy: Does the output violate content, privacy, or security policies?

I store eval results in the same system as deployment history so I can correlate a latency regression or cost spike with the exact code and model version that caused it. This sounds obvious, but most teams store evals in a spreadsheet and deployment history in GitHub Actions logs. Connect them.

3. Observability for AI Is Not Standard Observability

Standard APM tells you that a request took 800ms and returned HTTP 200. It does not tell you that the model generated a dangerously wrong configuration snippet, burned 12,000 tokens on a simple question, or called an internal API with parameters it hallucinated. You need AI-specific telemetry:

  • Prompt traces: Log the full prompt, the model version, the temperature/top-p settings, and the tool-call history
  • Token usage: Input tokens, output tokens, and cost per request, aggregated by user, team, and feature
  • Tool-call audit: Every external API the agent touches, with parameters, response status, and latency
  • Retrieval context: What documents or data were fetched, their relevance scores, and whether they were actually used
  • Human feedback: Thumbs up/down, corrections, escalations — this becomes your next eval dataset

I build this with OpenTelemetry where possible, because AI pipelines are just distributed systems with extra steps. The same tracing, correlation, and alerting patterns apply. The difference is the payload: prompts and embeddings instead of JSON request bodies.

4. Access Boundaries Keep Agents Safe

The most dangerous AI system is the one with broad permissions and no review gate. I use a tiered access model that mirrors human role-based access control:

  • Read-only agents: Can inspect logs, metrics, and documentation. Cannot change infrastructure. This covers 70% of operational use cases.
  • Approved-action agents: Can propose changes — scaling events, config updates, deployment rollbacks — but a human must approve before execution. This covers 25% of use cases.
  • Autonomous agents: Can act within narrow, pre-approved guardrails with full audit logging and automatic rollback triggers. This covers the remaining 5% and requires the strongest observability and eval coverage.

Every action is logged. Every tool call is traced. Every agent has a kill switch and a budget. If an agent's token spend exceeds its daily limit, it stops. If it makes three consecutive failed API calls, it stops and escalates. These are not constraints on innovation. They are the guardrails that let you sleep through the night.

5. You Need a Rollback Story

Model providers update their APIs, deprecate versions, and change behavior without warning. A prompt that worked yesterday can break today because the underlying model was silently patched. Your rollback strategy cannot be "revert the code" if the problem is the model version, not the code.

I version everything: prompts, model configs, retrieval indexes, and tool schemas. Each version is immutable. Each deployment references a specific version hash. Rollback means pointing at the previous hash, not editing files in production. This is GitOps for AI, and it is the only way to maintain sanity when you have multiple models, multiple prompts, and multiple teams shipping simultaneously.

6. Cost Guardrails Are Production Requirements

AI costs are unpredictable. A bug in a loop can turn a $0.02 request into a $200 request. A misconfigured retry policy can 10× your bill overnight. I treat cost exactly like latency or error rate: it gets an SLO, an alert, and an owner.

The controls I implement are simple and effective:

  • Per-user token budgets: Hard and soft limits with graceful degradation
  • Model routing: Route simple queries to cheaper models, reserve expensive models for complex tasks
  • Caching: Embed and cache frequent queries to avoid redundant token generation
  • Cost attribution: Tag every request with team, feature, and environment so finance can see who spent what

These are not FinOps afterthoughts. They are architectural decisions made at design time. Retrofitting cost controls into a live AI system is painful. Building them in from day one is trivial.

The Bottom Line

AI platform engineering is not fundamentally different from any other platform engineering. The same principles apply: clear ownership, strong testing, deep observability, tight access control, fast rollback, and cost discipline. The difference is that AI systems are less predictable, more expensive, and harder to debug when they go wrong. The margin for error is smaller, so the platform rigor must be higher.

If you are building AI features today, ask yourself these six questions before you ship: Who owns this? How do we evaluate it? What do we observe? What can it access? How do we roll back? How do we control cost? Answer them honestly, build the answers into your platform, and you will avoid the 2am pages that every unprepared AI team eventually gets.
